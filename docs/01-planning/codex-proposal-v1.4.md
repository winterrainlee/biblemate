# Codex Proposal: v1.4 (Planning)

- 작성일/작성자: 2026-01-09/GPT-5.2
- 검토일/검토자: 2026-01-09/Antigravity
- 2차 검토일/검토자: 2026-01-09/GPT-5.2
- 3차 검토일/검토자: 2026-01-12/Claude Opus
- 범위: v1.4에서 고려할 “로드맵 기반 추천 스코프” + “신규 제안(로드맵 외)” 정리

## 배경 / 문제
v1.3.x에서 백업/데이터 무결성을 강화한 흐름을 이어, v1.4에서는 **읽기 UX 개선(체감)**과 **운영 안정성/보안(서버)** 및 **에러 처리 일관성(서버+클라이언트)**을 함께 정리하면 제품 품질과 유지보수성이 크게 올라갑니다.

## 가정
- 배포는 Fly.io + Docker 기반이며, 프로덕션 도메인이 명확하다.
- 인증은 쿠키 기반 세션(`session_token`)이며 API는 `/api/*`로 제공된다.
- v1.4에서는 “큰 아키텍처 변경”보다 **작고 확실한 개선**을 우선한다.

## 항목 R1) 읽기 완료 버튼 개선

### 내용 설명
- 읽기 완료 기록 동작을 **명확하고 일관되게** 만든다.
- 중복 기록 방지, 성공/실패 피드백(토스트), 버튼 상태(로딩/완료됨) 등을 정리한다.

### 우선순위
- **P0 (Must)**

### 의존성
- 없음(현 구조에서 개선 가능)

### 필요 작업(작업 목록)
1. “완료” 동작의 기준 정의(예: 선택한 책/장 범위)
2. 동일 범위 중복 기록 방지(클라에서 사전 체크 + 서버에서 최종 방지)
3. 버튼 상태: `idle/loading/success/already_logged/error` 상태 표시
4. 토스트/애니메이션 등 피드백을 표준 컴포넌트로 정리(가능하면 공용)

### 완료 기준 (Acceptance Criteria)
- 동일 범위에서 “읽기 완료”를 반복 눌러도 기록이 중복되지 않음
- 성공/실패/이미 기록됨 케이스에 대해 사용자 피드백이 명확함

### 리스크 / 주의
- 읽기 범위 정의가 애매하면 UX 혼란이 생기므로 UI에 기준을 명시

## 항목 R2) 성경 읽기표 UI 개선 (팝업→페이지)

### 내용 설명
- 현재 상단 헤더의 버튼을 통해 팝업(Modal)으로 뜨는 **"성경 읽기표"를 별도 URL을 가진 전용 페이지**로 변경한다.
- 팝업이 모바일에서 좁고 답답한 문제를 해결하고, 전체 현황을 더 넓은 화면에서 직관적으로 볼 수 있게 한다.

### 우선순위
- **P0 (Must)**

### 의존성
- 없음

### 필요 작업(작업 목록)
1.  `/attendance` 또는 `/chart` 와 같은 전용 라우트 신설
2.  기존 `AttendanceModal` 컴포넌트를 독립 페이지 레이아웃으로 변환
3.  헤더 아이콘 클릭 시 모달 오픈 대신 페이지 이동으로 변경

### 완료 기준 (Acceptance Criteria)
- 성경 읽기표가 팝업이 아닌 전체 화면 페이지로 열림
- 뒤로가기(Back) 동작이 브라우저 히스토리와 자연스럽게 연동됨

## 항목 R3) Verse/범위 기반 읽기 기록(부분 읽기 체크)

### 내용 설명
- 단일 chapter 기록 중심에서 “부분 범위”를 더 정확히 표현한다.
- 현실적인 옵션은 2가지:
  - A) **챕터 범위(from/to)** 중심(현 `reading_logs` 모델과 정합)
  - B) **구절 범위(verse_from/to)** 또는 “읽은 구절 수”를 저장(스키마 확장 필요)

### 우선순위
- **P1 (Should)**

### 의존성
- 어떤 데이터 모델을 채택할지 결정(A/B)
- B 선택 시 DB 마이그레이션/기존 데이터 유지 전략 필요

### 필요 작업(작업 목록)
1. 범위 선택 UI(챕터 범위/구절 범위) 정의
2. 서버 API 및 DB 반영
3. 캘린더/통계(있다면)에서 부분 범위를 표시하는 규칙 정의

### 완료 기준 (Acceptance Criteria)
- 사용자가 “부분 읽기”를 기록할 수 있고, 목록/캘린더에 일관되게 표시됨

### 리스크 / 주의
- 구절 단위까지 가면 스키마/마이그레이션/UX 결정이 필요해 범위가 커질 수 있음

## 신규 제안 (로드맵 외)

## 항목 N1) 프로덕션 CORS 제한 (Origin Allowlist)

### 내용 설명
현재 서버는 `cors({ credentials: true, origin: true })` 형태로 사실상 “요청한 Origin을 그대로 허용”합니다. 쿠키 인증을 사용하는 구조에서 불필요하게 공격 표면이 넓고, 운영 중 문제 추적도 어려워집니다.

**목표**
- 프로덕션에서는 명시된 도메인(예: `https://biblemate.fly.dev`)만 CORS 허용
- 로컬 개발에서는 기존처럼 동작(또는 `http://localhost:5173` 등 제한)

### 우선순위
- **P0 (Must)**

### 의존성
- 프로덕션에서 사용하는 최종 도메인 리스트 확정
- 환경변수 설정(예: Fly secrets 또는 런타임 env)

### 필요 작업(작업 목록)
1. `ALLOWED_ORIGINS` 환경변수 정의 (CSV 또는 JSON 배열 문자열)
2. `server/index.js`에서 `origin`을 콜백 함수로 변경하여 allowlist 기반으로 판단
3. `NODE_ENV=production`일 때만 allowlist 강제, dev에서는 느슨하게 허용(또는 dev allowlist)
4. 허용되지 않은 Origin 요청 시 동작 정의
   - 브라우저 요청은 CORS에서 차단되도록 하고
   - 서버 로그에 origin 기록(디버깅용)
5. (선택) 문서 업데이트: 배포 가이드에 `ALLOWED_ORIGINS` 설정 방법 추가

### 완료 기준 (Acceptance Criteria)
- 프로덕션에서 허용된 Origin에서만 쿠키 포함 API 호출이 가능
- 허용되지 않은 Origin에서 브라우저 호출 시 CORS 차단됨
- 로컬 개발 흐름(`vite` 프록시)에서 기능이 깨지지 않음

### 리스크 / 주의
- 모바일/로컬 IP 접속 등 다양한 접근 경로가 있다면 allowlist에 반영 필요
- CORS는 “브라우저” 통제이며, 서버 자체 인증/인가를 대체하지 않음

## 항목 N2) API 응답/에러 표준화 (ok/error_code Contract)

### 내용 설명
현재 백업 API는 `{ ok, error_code, message }` 형태로 정리되어 있으나, 다른 라우트는 `{ error: ... }` 등 응답 형태가 제각각입니다. 이 상태에서는 클라이언트 에러 처리 로직이 분산되고, UX/디버깅/로깅이 어려워집니다.

**목표**
- 서버 API 전반에 대해 최소한의 일관된 계약을 제공
- 클라이언트는 `error_code`를 기준으로 일관된 메시지/행동(재로그인 유도 등)을 수행

권장 스펙(예시)
- Success: `{ ok: true, data: ... }`
- Failure: `{ ok: false, error_code: "CODE", message: "...", details?: ... }`

### 우선순위
- **P1 (Should)**

### 의존성
- 우선 적용 범위 결정(권장: 인증/공통 오류부터)
- 클라이언트 공통 API 래퍼(`client/src/services/api.js`) 확장 여부 결정

### 필요 작업(작업 목록)
1. **서버 에러 코드 카탈로그 초안** 정의
   - 예: `UNAUTHORIZED`, `INVALID_REQUEST`, `NOT_FOUND`, `DB_ERROR` 등
2. 가장 영향 큰 경로부터 단계적 적용
   - (1단계) 인증 실패(401) 응답을 전 라우트에서 동일 형태로 보장
   - (2단계) 입력 검증(400)과 서버 오류(500)도 동일 형태로 정리
3. `client/src/services/api.js`에서
   - 응답 body의 `ok/error_code/message`를 우선 처리
   - `401` 발생 시 UI에서 재로그인 유도 흐름 통일
4. (선택) 서버 공통 에러 핸들러/유틸 함수 도입(중복 감소)

### 완료 기준 (Acceptance Criteria)
- 주요 API에서 실패 시 `error_code`가 항상 제공됨(최소 401/400/500)
- 클라이언트는 `error_code` 기반으로 사용자 메시지/행동이 통일됨
- 로그/디버깅 시 `error_code`로 원인 분류가 가능

### 리스크 / 주의
- 한 번에 전체 라우트를 바꾸면 범위가 커질 수 있으므로 단계적 적용 권장
- 기존 클라이언트가 특정 응답 형태를 가정하는 부분이 있으면 회귀 테스트 필요

## 검토 의견 (Antigravity)

전반적으로 v1.3.1 이후의 안정화와 UX 개선을 위한 합리적인 제안입니다. 특히 **P0 항목들(R1, R2, R4, N1)**은 즉각적인 사용성 향상과 보안 강화를 위해 필수적입니다.

### 세부 피드백

1.  **R3 (부분 읽기/구절 범위)에 대한 제언**
    - 현재 챕터 단위 `reading_logs`는 "완료"의 의미가 강합니다. 부분 읽기를 위해 기존 테이블을 수정하기보다, **`reading_progress`와 같은 별도 테이블(혹은 컬럼)**로 "마지막으로 읽은 위치(Verse)"를 저장하는 방식을 추천합니다.
    - 이렇게 하면 "읽기 로그(History)"와 "현재 진행 상태(Progress)"를 분리하여 관리할 수 있어 데이터 모델이 더 깔끔해질 수 있습니다.

2.  **데이터 마이그레이션 전략 (R3, R5 관련)**
    - SQLite 특성상 컬럼 속성 변경(Unique 제약 해제 등)이 까다로울 수 있습니다(테이블 재생성 필요).
    - v1.4 배포 시, 서버 구동 단계에서 자동으로 DB 스키마를 마이그레이션하는 스크립트(`migrate.js` 등)의 안정성 검증이 매우 중요합니다.
    - 사용자별 로컬 DB파일(.db)을 사용하는 구조라면, 배포 후 첫 접속 시 마이그레이션 로직이 실패하지 않도록 방어 코드가 필요합니다.

3.  **N2 (에러 표준화) 우선순위**
    - P1으로 잡혀있으나, 클라이언트 코드를 건드리는 김에 **R1(완료 버튼 개선)**과 함께 진행하는 것이 효율적일 수 있습니다. UX 개선 시 에러 상황(이미 읽음, 네트워크 오류 등) 피드백이 중요하기 때문입니다.

4.  **종합 의견**
    - **R1, R2, R4, N1**을 우선 진행하여 v1.4.0을 릴리즈하고, 스키마 변경이 필요한 R3, R5는 v1.4.1 혹은 v1.5.0으로 분리하는 것도 고려해볼 만합니다(리스크 분산).

## 2차 검토 의견 (GPT-5.2)

Antigravity의 검토 의견에 동의하며, 특히 **스키마 변경(R3/R5)의 리스크 분산**과 **로그(History) vs 진행(Progress) 분리**는 v1.4 품질을 좌우하는 핵심 포인트입니다.

### 1) R3 방향(부분 읽기) 재정의 제안
- `reading_logs`는 “읽은 기록(히스토리)”로 유지하고, 부분 읽기/이어읽기는 별도 상태로 분리하는 편이 깔끔합니다.
- 권장 모델: `reading_progress` 테이블(또는 단일 row key-value)로 `(book, chapter, verse)`의 “마지막 위치”를 저장.
- UI 측면에서도 “오늘 읽은 것(로그)”과 “이어 읽기(진행)”가 분리되면 사용자가 이해하기 쉽습니다.

**권장 결론**
- v1.4.0에는 R3를 넣지 않고(또는 챕터 범위(from/to)까지만), 구절 단위 진행은 v1.4.1로 분리.

### 2) 마이그레이션 전략 구체화(실행 안정성)
- sql.js는 DB를 메모리에 올려 변경 후 파일로 write-back하는 구조라, 마이그레이션 실패 시 복구가 중요합니다.
- 권장 절차:
  1. 부팅 시 `PRAGMA user_version` 또는 별도 `schema_meta`로 스키마 버전 확인
  2. 마이그레이션 전에 DB 파일 백업(`bible.db.bak` 등)
  3. 마이그레이션 수행(테이블 재생성/데이터 복사 포함)
  4. 성공 시 `saveDB()` 호출 후 `.bak` 보관/삭제 정책 적용
  5. 실패 시 롤백/복구 경로 제공(최소: 서버 로그 + 백업 복원)

### 3) N2(에러 표준화) 실행 전략 보완
- Antigravity 의견대로 R1을 손보는 김에 N2를 “완전 적용”이 아니라 **1단계만 동시 적용**하는 것이 효율적입니다.
- 권장 1단계 범위(v1.4.0):
  - `401`/`403`는 전 라우트에서 `{ ok:false, error_code:"UNAUTHORIZED", message }` 형태 보장
  - 클라이언트는 `error_code` 기반으로 재로그인 유도 메시지 통일
- 나머지(400/500 표준화)는 v1.4.1로 미루면 범위를 통제할 수 있습니다.

### 4) R5(다중 하이라이트) 범위 조정
- 스키마 변경이 동반되므로 v1.4.0보다는 v1.4.1로 분리하는 편이 안정적입니다.
- v1.4.0에서는 UI/UX 선행 작업(스타일 선택 UI, 단일 하이라이트 삭제/변경 UX)을 정리해두면 v1.4.1 구현이 쉬워집니다.

### 종합 제안(릴리즈 전략)
- **v1.4.0**: R1, R2, R4, N1 + N2(1단계: auth 에러 통일)
- **v1.4.1**: R3(진행 테이블 도입 포함), R5(스키마 변경), N2(400/500까지 확대)

## 3차 검토 의견 (Claude Opus)

전체적으로 잘 구조화된 v1.4 제안서입니다. Antigravity와 GPT-5.2의 검토 의견에 전반적으로 동의하며, 몇 가지 추가 관점을 제시합니다.

### 1) 릴리즈 전략 승인
v1.4.0과 v1.4.1 분리 전략은 **리스크 관리 측면에서 매우 합리적**입니다:
- **v1.4.0**: R1, R2, R4, N1 + N2(1단계) → 빠른 UX 개선 + 보안 강화
- **v1.4.1**: R3, R5, N2(2단계) → 스키마 변경 포함된 고위험 작업

### 2) N1(CORS) 구현 시 주의사항
- `origin: true`에서 allowlist로 전환 시, **프리플라이트(OPTIONS) 요청 처리**도 함께 검토 필요
- Fly.io 배포 시 `*.fly.dev` 외에 커스텀 도메인을 사용한다면 allowlist에 포함 필요

### 3) R2(읽기표 페이지화) 추가 제안
- 페이지 전환 시 **URL 공유 가능성**을 고려하면 `/chart?book=창세기` 같은 쿼리 파라미터 지원이 유용할 수 있음
- 이는 v1.4.0 필수는 아니지만 향후 확장성 측면에서 라우트 설계 시 고려 권장

### 4) 문서 품질 평가
- 요약표, 완료 기준(Acceptance Criteria), 리스크 항목이 잘 정리되어 있어 **구현 시 명확한 가이드라인** 역할을 할 것으로 보임
- 각 항목별 의존성이 명시되어 있어 작업 순서 결정에 도움됨

### 종합 평가
