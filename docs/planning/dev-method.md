# 개발 방법론
저는 초보 바이브 코딩 개발자라서, 개발 시 혼란을 줄이기 위해 방법론을 준비했습니다.

## 1. 목표 정렬과 범위 설정
핵심 가치(말씀 읽기/묵상/진도·UX)를 다시 확인하고, 다음 버전에서 개선·확장할 포인트를 세분화합니다. 예) 이중 역본 전환 UX 개선, 노트 자동저장 안정성, 모바일 반응형 최적화 등.

기능 영역별로 기대 결과(사용자 스토리·정량 목표)와 “완료” 정의를 명확히 적습니다. 읽기/노트/진도/설정 네 축으로 나누면 추적이 쉽습니다.

## 2. 구조 기반의 워크스트림 쪼개기
백엔드: server/routes/의 도메인별 라우트(bible/highlights/notes/reading) 단위로 이슈를 나누고, 스키마 변화가 필요한지 먼저 검토합니다.

프론트엔드: client/src/pages/ReadingDashboard.jsx 등 페이지 단위로 UX 변화 범위를 정의한 뒤, 공용 컴포넌트(components/)와 서비스 래퍼(services/api.js) 영향도를 체크합니다.

데이터 흐름: 장·구절 조회, 하이라이트, 노트 저장, 읽기 로그의 요청 순서를 기준으로, 병목이 생길 지점(예: 저장/조회 동시성, 캐싱 필요성)을 사전에 명세합니다.

## 3. 계획 산출물 템플릿
로드맵 표: 기능 테마별(읽기/노트/진도/설정)로 에픽 → 스토리 → 기술 태스크를 계층화하고, 위험도·복잡도 점수로 우선순위화.

인터페이스 계약: 변경 예상 API의 요청/응답 스키마와 실패 케이스를 간단한 표로 정리(예: 새 필터 추가 시 GET /reading/logs?book=... 응답 필드 정의).

UI 영향도 지도: 페이지/컴포넌트/스타일 파일 경로를 적시해 개발자가 바로 위치를 찾도록 합니다.

## 4. 실행·검증 루프
빠른 검증을 위해 페이지별로 최소 단위의 “기능 플래그”나 “옵션 토글”을 두어 부분 배포/리뷰를 쉽게 합니다.

QA 시나리오를 데이터 흐름 단계(조회→하이라이트→노트→저장) 순서로 작성해 회귀 범위를 줄입니다.

## 5. 협업·온보딩 최적화
새 기여자에게는 npm run dev 등 기본 실행 경로와 백엔드만 돌리는 옵션을 함께 안내하여 셋업 시간을 줄입니다.

## 6. 작업 흐름도

### 일반 흐름 (Minor/Major)
1. 희망 아이템 및 Bug 발견 사항을 **Inbox**에 자유롭게 추가합니다.
2. Inbox 아이템을 `[Major]`/`[Minor]`/`[Patch]` 라벨과 함께 **Categorized items**로 분류합니다.
3. 우선순위 선별을 통해 차기 버전에 포함할 작업을 결정하고, **목표 버전**을 설정합니다.
4. AI 협업 규칙 (승인 게이트)
   - 승인 없이 범위/요구사항 변경 금지: 명세의 A를 B로 대체하거나 생략하고 싶다면, 실행 전에 반드시 질문하고 사용자 승인을 받습니다.
   - 결정 필요 시 즉시 정지: 구현 중 결정이 필요한 사항이 발생하면 코드 변경을 즉시 중단하고 사용자에게 질문합니다.
   - 질문 형식 고정: 아래 순서로 제시합니다.
   “결정이 필요한 이유 → 선택지 2~3개 → 각 장단점/위험 → 추천안”
   - 단계 이동 금지: 현재 단계 산출물이 ‘계획서/검증서’라면, 사용자가 “진행”이라고 답하기 전까지 실제 코드 수정/리팩터링을 시작하지 않습니다.
   - 변경 로그: 합의된 변경(요구사항/파일/데이터)은 이유를 포함하여 dev-log에 한 줄로 남깁니다
5. **개발용 브랜치 생성**: `feature/v버전명` 브랜치를 생성하고 체크아웃합니다.
   - **Tip**: 개발 중 문서(`docs/`) 수정도 자유롭게 커밋하세요. 나중에 Squash Merge로 깔끔하게 합쳐집니다.
6. 버전 명세서를 작성합니다. (`spec-v버전명.md`)
   - 복수의 AI 에이전트 검토를 거쳐 확정
7. 명세서를 기반으로 개발을 진행합니다. 진행 상황과 장애, 해결책, lessons learned 등을 로그에 기록합니다. (`logs/dev-log-v버전명.md`)
8. 개발 완료 후 검증 및 수정을 진행합니다. 검증 상황과 오류, 해결책, lessons learned 등을 로그에 기록합니다. (`logs/verification-v버전명.md`)
9. Release Notes를 작성하고 배포합니다. (`logs/release-notes-v버전명.md`)
10. 배포 후, 완료된 작업을 **Completed** 섹션으로 이동합니다.
11. 차기 버전 흐름으로 이어갑니다.

### 긴급 흐름 (Patch/Hotfix)
0. 치명적 버그 발생 시 단축 경로를 사용합니다. Hotfix는 마지막 릴리즈 태그에서 분기해서 수정하고, 상위 브랜치(main)에도 반영합니다. 상위 브랜치 이름은 main을 권장하나, 이미 master로 설정되어 있다면 master를 사용합니다.
1. Bug Revealed에 이슈 등록
2. 즉시 수정 및 테스트
3. Release Notes 작성 후 배포 (`logs/release-notes-v버전명.md`)
4. Completed 섹션으로 이동

### 배포 절차 (Minor/Major)
개발 완료 후 배포 프로세스입니다.
1. **버전 표시 업데이트**
   - `package.json`: version 업데이트
   - `Settings.jsx`: 버전 표시 업데이트
   - `README.md`: 버전 및 기능 설명 업데이트
   - `roadmap.md`: 최신 배포 버전 업데이트
2. **Git 작업**
   - `git branch -a`로 상위 브랜치 이름 확인 (main 또는 master)
   - 변경사항 커밋
   - 상위 브랜치로 squash merge
   - 버전 태그 생성 (예: `v1.1`)
   - 원격 저장소 푸시
   - feature 브랜치 삭제
3. **GitHub Release 생성**
   - Release Notes 첨부
4. **문서 정리**
   - roadmap Completed 섹션 업데이트
   - docs-index.md 링크 추가


## 7. 버전 관리 기준

### Major 버전 (2.0, 3.0, ...)
대규모 아키텍처 변경이나 핵심 사용자 경험이 근본적으로 바뀔 때 올립니다.
- **DB 스키마 대폭 변경**: 기존 데이터 마이그레이션이 복잡하거나 호환 불가
- **핵심 기능 재설계**: 읽기/노트/진도 중 하나의 워크플로우가 완전히 변경
- **다중 사용자 지원 도입**: 로그인/인증 시스템 추가 (단일→멀티 유저)
- **AI 기능 도입**: 외부 API 연동 및 새로운 상호작용 모드 추가

### Minor 버전 (1.1, 1.2, ...)
기존 구조 내에서 기능을 추가하거나 개선할 때 올립니다.
- **신규 기능 추가**: 백업/복구, 역본 대조, 통독 플랜 등
- **UI/UX 개선**: 반응형 최적화, 다크모드 보완, 접근성 강화
- **성능 향상**: 로딩 속도 개선, 캐싱 도입
- **버그 수정 묶음**: 여러 버그를 함께 수정하여 릴리즈

### Patch 버전 (1.1.1, 1.1.2, ...)
긴급 버그 수정이나 사소한 변경에 사용합니다.
- **핫픽스**: 치명적 버그 긴급 수정
- **오타/문구 수정**: 사용자에게 보이는 텍스트 교정
- **의존성 보안 패치**: 라이브러리 취약점 대응

## 8. Lessons Learned (교훈)

### 방법론의 중요성
BibleMate v1.0과 v1.1을 개발하면서 배운 가장 중요한 교훈:

#### 1. 문서화는 선택이 아닌 필수
- 코드는 금방 잊혀진다
- 문서는 "미래의 나"를 위한 투자
- 특히 AI와 협업할 때 컨텍스트 제공에 필수

#### 2. 방법론 세팅이 속도를 결정
- 초기에 시간을 들여 방법론을 만들면
- 이후 모든 버전 개발이 빨라진다
- "어떻게 할까?" 고민 시간이 사라짐

#### 3. 체크리스트의 힘
- 머리로 기억하지 말고 문서로
- 놓치는 것 없이 안정적으로 배포
- 반복 작업을 시스템화

#### 4. 워크스페이스 문서 vs 아티팩트
- **중요한 문서는 워크스페이스의 실제 파일로 작성**
- IDE가 비정상 종료되면 세션이 끊길 수 있음
- 아티팩트는 임시 작업용, 실제 문서는 프로젝트 폴더에
- 꾸준히 수정하고 Git으로 버전 관리

> 💡 **핵심**: 이 프로세스는 다른 프로젝트에도 재사용 가능하며, 개발 생산성을 극대적으로 높여준다.
